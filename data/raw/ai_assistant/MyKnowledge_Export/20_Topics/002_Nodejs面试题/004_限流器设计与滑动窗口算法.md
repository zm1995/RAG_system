## 面试题

 > 
 > 设计一个限流器，防止某个 API 被同一 IP 每秒调用超过 10 次。

---

## 核心答案（三层结构）

### 第一层：数据结构

用 `Map<string, number[]>` 存储每个 IP 的访问时间戳数组。

### 第二层：滑动窗口算法

每次请求时，计算 `windowStart = now - 1000ms`，过滤掉窗口之外的时间戳，剩余数量即为当前窗口内的请求数。

### 第三层：策略

* 超过限制 → 返回 429，带 `Retry-After` 头
* 未超过 → 记录当前时间戳，放行

---

## 核心代码

````javascript
class SlidingWindowRateLimiter {
  constructor(limit = 10, windowMs = 1000) {
    this.limit = limit;
    this.windowMs = windowMs;
    this.requests = new Map();
  }

  allow(ip) {
    const now = Date.now();
    const timestamps = this.requests.get(ip) || [];
    const windowStart = now - this.windowMs;
    const valid = timestamps.filter(t => t > windowStart);

    if (valid.length >= this.limit) {
      return false;
    }

    valid.push(now);
    this.requests.set(ip, valid);
    return true;
  }
}
````

### ⚠️ 面试官追问1：固定窗口 vs 滑动窗口 vs 令牌桶

|算法|优点|缺点|适用场景|
|--|--|--|----|
|**固定窗口**|实现简单|边界突刺问题（59秒-61秒可能瞬间双倍流量）|不推荐|
|**滑动窗口（你选的）**|平滑、公平|需要存储每个请求的时间戳，内存占用随QPS增长|通用推荐|
|**令牌桶**|允许突发流量|实现稍复杂|需要允许短时突发的场景|

**面试时你可以这样说：**

 > 
 > "我选择滑动窗口，因为它比固定窗口更平滑，不会出现边界突刺。如果流量特别大，我会考虑用 Redis 的 Sorted Set 来替代内存存储，实现分布式限流。"

---

### ⚠️ 面试官追问2：超过限制后，你是直接拒绝还是排队等待？

你说"直接拒绝"和"排队等待"都提到了，面试官会问你**你的选择是什么**。

* **直接拒绝（返回429）**：简单、不消耗资源，适合大部分API

* **排队等待**：适合对成功率要求极高的场景（如支付回调），但需要实现异步队列

**面试时你可以这样说：**

 > 
 > "我会选择**直接拒绝**，因为排队等待会消耗服务器资源，且增加请求延迟。我会在响应头里带上 `Retry-After: 1`，告诉客户端1秒后再试。如果业务确实需要排队，我会用消息队列（如Bull/RabbitMQ）来实现异步处理，而不是在限流器里做同步等待。

## 📝 方案一：单机版（内存实现）

````javascript
class SlidingWindowRateLimiter {
  constructor(limit = 10, windowMs = 1000) {
    this.limit = limit;           // 窗口内允许的最大请求数
    this.windowMs = windowMs;     // 窗口大小（毫秒）
    this.requests = new Map();    // key: ip, value: 时间戳数组
  }

  /**
   * 检查是否允许请求
   * @param {string} key - 限流的key（如IP、用户ID）
   * @returns {boolean} true=允许，false=拒绝
   */
  allow(key) {
    const now = Date.now();
    const timestamps = this.requests.get(key) || [];
    
    // 1. 滑动窗口：只保留窗口内的时间戳
    const windowStart = now - this.windowMs;
    const validTimestamps = timestamps.filter(t => t > windowStart);
    
    // 2. 判断是否超过限制
    if (validTimestamps.length >= this.limit) {
      return false;
    }
    
    // 3. 记录本次请求，放行
    validTimestamps.push(now);
    this.requests.set(key, validTimestamps);
    return true;
  }

  /**
   * 定时清理过期key（防止内存泄漏）
   * 每5分钟清理一次
   */
  startCleanup() {
    setInterval(() => {
      const now = Date.now();
      const windowStart = now - this.windowMs;
      for (const [key, timestamps] of this.requests) {
        const valid = timestamps.filter(t => t > windowStart);
        if (valid.length === 0) {
          this.requests.delete(key);
        } else {
          this.requests.set(key, valid);
        }
      }
    }, 5 * 60 * 1000);
  }
}

// 使用示例
const limiter = new SlidingWindowRateLimiter(10, 1000);
if (limiter.allow('192.168.1.1')) {
  // 处理请求
} else {
  // 返回 429 Too Many Requests
}
````

## 📝 方案二：分布式版（Redis + Lua 脚本）

### 为什么需要分布式方案？

单机版在**多实例部署**时失效——如果 Nginx 把请求分发给 3 个 Node 实例，每个实例有各自的计数器，限流就形同虚设。**Redis 作为共享存储，是所有分布式限流的共同选择。**

### Lua 脚本（原子性保证）

````lua
-- rate_limiter.lua
-- KEYS[1]: 限流的key（如 ip:192.168.1.1）
-- ARGV[1]: 窗口大小（毫秒）
-- ARGV[2]: 限制数量
-- ARGV[3]: 当前时间戳（毫秒）

local key = KEYS[1]
local window_ms = tonumber(ARGV[1])
local limit = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

-- 1. 移除窗口外的过期记录（滑动窗口）
redis.call('ZREMRANGEBYSCORE', key, 0, now - window_ms)

-- 2. 获取当前窗口内的请求数
local current_count = redis.call('ZCARD', key)

-- 3. 判断是否超限
if current_count < limit then
    -- 4. 未超限：记录本次请求（member 用 时间戳+随机数 保证唯一）
    redis.call('ZADD', key, now, now .. ':' .. math.random(1000000))
    -- 5. 设置过期时间（窗口大小 + 1秒，防止僵尸key）
    redis.call('EXPIRE', key, math.ceil(window_ms / 1000) + 1)
    return 1  -- 允许
else
    return 0  -- 拒绝
end
````

### Node.js 调用端

````javascript
const redis = require('ioredis');
const client = new redis({
  host: 'localhost',
  port: 6379,
  // 生产环境：连接池配置、超时、重试策略
});

class RedisSlidingWindowLimiter {
  constructor(limit = 10, windowMs = 1000) {
    this.limit = limit;
    this.windowMs = windowMs;
    this.scriptSha = null;
  }

  /**
   * 初始化：将 Lua 脚本加载到 Redis
   * 生产环境建议在应用启动时预加载
   */
  async init() {
    const script = `-- 完整Lua脚本（见上面的代码块）`;
    this.scriptSha = await client.script('LOAD', script);
  }

  /**
   * 检查是否允许请求
   * @param {string} key - 限流key
   * @returns {Promise<boolean>}
   */
  async allow(key) {
    const now = Date.now();
    const result = await client.evalsha(this.scriptSha, {
      keys: [key],
      args: [String(this.windowMs), String(this.limit), String(now)],
    });
    return result === 1;
  }
}

// 使用示例
const limiter = new RedisSlidingWindowLimiter(10, 1000);
await limiter.init();

// 在路由中使用
app.use(async (req, res, next) => {
  const key = `ip:${req.ip}`;
  const allowed = await limiter.allow(key);
  if (!allowed) {
    return res.status(429).json({ error: 'Too Many Requests' });
  }
  next();
});
````

## 🎯 面试官追问及回答

|追问|回答|
|--|--|
|**为什么用 Lua 脚本？**|保证 **原子性**。Redis 中 ZREMRANGEBYSCORE 和 ZCARD 是两个命令，如果分两次执行，中间可能有并发请求趁虚而入。Lua 脚本在 Redis 中执行时是单线程的，不会被中断。|
|**如果 Redis 挂了怎么办？**|两种策略：(1) **降级**：本地内存限流+告警；(2) **熔断**：直接返回 429，防止服务被打垮。生产环境需要配置 Redis 哨兵/集群保证高可用。|
|**窗口内的时间戳越来越多，内存怎么办？**|每次请求用 `ZREMRANGEBYSCORE` 清理过期数据，且设置了 `EXPIRE` 自动过期。单个 key 最多存储 `limit + 1` 条记录（因为超限后就不再新增），内存可控。|
|**为什么不直接用 INCR + EXPIRE 做固定窗口？**|固定窗口有**边界突刺**问题：用户在 59.9秒 和 60.1秒 分别发 10 次请求，实际 0.2 秒内发 20 次，突破了限制。滑动窗口更平滑，精确到毫秒级。|
|**限流后怎么告诉客户端重试？**|返回 `HTTP 429`，并在响应头添加 `Retry-After: 1`（单位：秒），告诉客户端 1 秒后再试。|

## 💡 面试金句（背下来）

 > 
 > "限流器的核心是**时间窗口 + 计数器**。单机版用 Map 存时间戳数组，通过 `filter` 实现滑动。分布式版用 Redis 的 **Sorted Set** 作为共享存储，用 **Lua 脚本** 保证原子性——先 `ZREMRANGEBYSCORE` 移除过期记录，再 `ZCARD` 判断计数。生产环境我会配合 `Retry-After` 头和降级策略，确保系统在面对突发流量时保持弹性。"
